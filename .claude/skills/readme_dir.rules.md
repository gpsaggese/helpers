Conventions for writing a README for a directory with executables

# Scope and Naming

- Use these rules for the `README.md` of a directory
  - For the README of a single executable / script, follow
    `.claude/skills/readme_file.rules.md`
- Follow the template `.claude/templates/readme_dir.template.md`
- To write the README, use the skill `.claude/skills/readme_dir.create/SKILL.md`

# Overall Structure

- Start the README with the title, then the bullet that says how it was generated
  ```markdown
  - Generated by `.claude/skills/readme_dir.create/SKILL.md`
  ```
- READMEs for a directory should follow this hierarchical organization:
  - **Summary**: Bold-labeled bullets (Goal, Input, Output, Users) describing the
    directory's purpose
  - **Structure of the Dir**: List subdirectories with <20-word descriptions
  - **Description of Files**: Alphabetical list of all files with 1-line descriptions
    in a table
  - **Description of Executables**: Detailed docs for each script/tool in a table
  - **Output Dir** (optional): Names and layout of the files that the executables
    write, as part of the executables section
  - **Description of Workflows** (optional): How executables combine for complex
    features
  - **Description of Architecture**: How code is organized in each directory
  - **Review roadmap**: Last section, with the map of the dir, the way to run the
    tests, and the table of the files with the time to read each one

# Writing Conventions

- Follow `.claude/skills/markdown.rules.md` and `.claude/skills/text.rules.md` for
  text formatting
- Keep descriptions concise and action-oriented
- Limit descriptions to specified word counts
- Write bullets, not prose paragraphs
  - This includes the intro of each section, e.g., the intro of "Description of
    Files" and of "Description of Executables"
  - Turn a sentence that lists many items into a bullet with one sub-bullet per item
- Keep the commands in every example in sync with the current CLI
  - Use only the args that the tool accepts now
  - When an arg is dropped or renamed, fix every example in the README, including
    the examples in the workflows

# Section Details

## Summary Section

- Use bullets with a bold label, and no prose paragraph
  - **Goal**: What the directory does, in one bullet
  - **Input**: What the executables read
  - **Output**: What the executables write
    - With many outputs, use one sub-bullet per file or per group of files
    - Do not list them in one long sentence
  - **Users**: Who uses the directory and for what
- Answer: _"What does this directory do?"_
- Example:
  ````markdown
  - **Goal**: Code and docs of a pipeline that turns a list of academic papers into a
    CSV report of candidate trading strategies.

  - **Input**: a CSV with one paper per row, as a title, link, DOI, or local PDF
  - **Output**:
    - A papers file and an issues file from `resolve_papers.py`, both JSON
    - `04-report.references.md`, `04-report.report.csv`, and `04-report.issues.csv`
    - The PDF, markdown, features file, and rating file of each paper
  - **Users**: quant researchers, who sort the CSV to pick the next papers to
    replicate
  ````

## Structure of the Dir Section

- Bullet list of subdirectories (if any) in a markdown table
- Format: `<dirname>/` followed by description (<20 words)
- Example:
  ```markdown
  | File                                   | Description    |
  | -------------------------------------- | ---------------|
  | `ai.claude_code.how_to_guide_figs/`    | Screenshots and images for Claude Code setup and usage guide |
  | `ai.github_copilot_review.how_to_guide_figs/` | Screenshots demonstrating GitHub Copilot review workflow |
  ```

## Description of Files Section

- Start with one bullet that gives the scope and the order, e.g., "Python and
  Markdown files, alphabetical by path."
- List all Python and Markdown files in directory formatted in a markdown table
- Alphabetical order for consistency
- `Description` is a <20 words description
- `Cluster` is the functionality
- Example:
  ```markdown
  | File                                   | Description                                                                  | Cluster             |
  | -------------------------------------- | ---------------------------------------------------------------------------- | ------------------- |
  | `bookmark_utils.py`                    | Shared helpers for downloading/uploading Google Sheets data and CSV files    | Shared Utilities    |
  | `download_academic_paper_to_md.py`     | Download an academic paper (arXiv/DOI/PDF), convert to Markdown, summarize   | Content Downloaders |
  | `download_to_md.py`                    | Detect input type and dispatch to the matching `download_*_to_md.py` script  | Content Downloaders |
  | `download_utils.py`                    | Shared helpers for fetching article titles and summarizing text via an LLM   | Shared Utilities    |
  | `podcast_dl.py`                        | Download and format a podcast transcript from various sources                | Podcast Tools       |
  ```

## Description of Executables Section (if Applicable)

- Find all executable files and create one `##` header per tool
- Start with bullets that say how many executables there are and how they relate

### Tables for Command References

- Find all executable filesS
- Use Markdown tables for many related commands
- **Column headers**: Name | Description
- One-sentence descriptions
- **Good for**: git commands, utility scripts, CLI tools
- **Format**:
  ```markdown
  | Command | Description |
  | :------- | :------- |
  | `command1` | What it does |
  | `command2` | What it does |
  ```

### For Each Executable

- Find all executable files and create one `##` header per tool
- **What It Does**: 1-3 bullets describing tool's purpose
  - Mention important inputs, outputs, and side effects
  - Use bullet points for clarity
  - Keep each bullet to one sentence
- **Examples**: 3-5 realistic usage patterns ordered simple → complex
  - Start with short description
  - Follow with fenced bash code block (see format rules below)
  - Include example output if helpful

### Format of Commands

- Commands as bullet + fenced code block:
  ````markdown
  - Description of what this command does:
    ```bash
    > command --arg value
    ```
  ````

- Break long commands with `\` for readability, indent continuation lines by 4 spaces:
  ````markdown
  - Generate slides with navigation breadcrumbs:
    ```bash
    > notes_to_pdf.py \
        --input lecture.txt \
        --output lecture.pdf \
        --type slides
    ```
  ````

- Use `> ` prefix (no `$` prompt)
- Do NOT use bold headers (`**text**`) for example descriptions
- Each example must have a bullet point with description and indented code block
- Each example must run with the current CLI of the tool
  - Remove an arg that the tool dropped, and rename an arg that the tool renamed
  - Check the examples of the workflows too, not only the examples of each executable

**Example of correct format:**

```markdown
- Generate slides with navigation breadcrumbs:
  ```bash
  > notes_to_pdf.py \
      --input lecture.txt \
      --output lecture.pdf \
      --type slides
  ```
```

### Inline Commands

- Short commands in prose (e.g., `run foo.py`) stay inline with backticks
- Only standalone usage instructions use bullet + fenced block format

## Output Dir Section (if Applicable)

- Add this section when the executables write a tree of files in one dir
- Use the header `## Output Dir`
- Put it after the overview of the executables and before the section of the first
  executable
- Use these parts, in this order:
  - **Intro bullets**: the arg that gives the dir, who names the files, and what a
    rerun skips
  - **Naming scheme**: one bullet with the name pattern and the meaning of each part
    - E.g., `NN-<stage>.<what>.<ext>`, where `NN` is the order of the executable
  - **Layout**: the tree of the dir in a fenced `text` block
  - **File table**: one row per file or per group of files, with the columns
    `File | Written by | Content`
  - **Why this layout**: one bullet per choice
    - Link each choice to its design decision, with a link from the repo root and
      an anchor
    - E.g., ``[`D29`](/path/to/docs/03-decisions.md#d29-numbered-stage-files-in-the-output-dir)``
  - **Closing bullet**: the code file that defines the names, and the rules file
    that governs the layout
- Example:
  ````markdown
  ## Output Dir

  - Every executable takes `--output_dir`, and the dir is the only place where files
    are written
    - The user gives the dir, and the executables infer the name of every file
    - A rerun on the same dir skips the work that is done
  - A file that a stage writes is named `NN-<stage>.<what>.<ext>`, where `NN` is the
    order of the executable
    ```text
    <output_dir>/
        00-paper_list.csv
        01-resolve.paper_list.json
        04-report.report.csv
        papers/
            <BASE>.pdf
            <BASE>.md
        state/
            cache/
            logs/
    ```
  - The files:

    | File                         | Written by           | Content                    |
    | :--------------------------- | :------------------- | :------------------------- |
    | `00-paper_list.csv`          | `resolve_papers.py`  | Copy of the input CSV      |
    | `01-resolve.paper_list.json` | `resolve_papers.py`  | The resolved papers        |
    | `04-report.report.csv`       | `report_papers.py`   | One row per rated paper    |
    | `papers/<BASE>.pdf`, `.md`   | `download_papers.py` | The paper and its markdown |

  - Why this layout
    - The number gives the order of the pipeline, so a listing of the dir reads from
      the input to the report
      ([`D29`](/research/Estimate_academic_paper_quality/docs/03-decisions.md#d29-numbered-stage-files-in-the-output-dir))
    - `state/` holds only the cache and the logs, which are not results of a stage
  - The names are in `research/Estimate_academic_paper_quality/epq_paths.py`, and the
    rules are in `.claude/skills/architecture.rules.md`
  ````

## Review Roadmap Section

- Use the header `# Review roadmap` as the last section of the README
- The skill `.claude/skills/review.create_code_tour/SKILL.md` reads this section to
  write the checklist that guides the review of the dir, so keep the parts and the
  order below
- Use these parts, in this order:
  - **Intro bullets**: the use of the section, and the path of the checklist file
    `code_tour.md`
  - **Map**: bullets with the purpose, the entry points in run order, the layers
    bottom first, and the cycles in the import graph
    - Write the path from the repo root for every file, with one line of purpose
  - **Testing** (`## Testing`): the commands to run the tests, in the dev env and in
    Docker
  - **Files and Reading Time** (`## Files and Reading Time`):
    - The reading speeds, in lines per min, and the total time to read every file
    - A bullet with the order of the rows of the table
    - The table, with the columns of the template
    - The `Skipped` line, and the notes on the table
- Order the rows by kind: `code`, `doc`, `test`, `data`
  - Order the `code` rows bottom up in the import graph, with the entry points last
  - Say the order in a bullet above the table, and say that it differs from the order
    of the checklist, which mixes the kinds
- Write the paths from the repo root in all the columns of the table, so that the
  reader can open them
- The README is a row of the table: set its `Lines` to the size of the final README
- Example: the last section of
  `research/Estimate_academic_paper_quality/README.md`
