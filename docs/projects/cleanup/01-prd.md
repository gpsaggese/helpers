# Cleanup Product Requirements

- Generated by `.claude/skills/project.write_prd/SKILL.md`

## Goal

- Make `helpers` a general-purpose library and dev system that any project can use
  without:
  - Causify accounts
  - AWS infrastructure
  - `CSFY_*` env vars
- Use one package manager (`uv`), one linter framework (`linters2/`), and a clean
  repo root
- Background:
  - The idea and the walkthrough findings:
    [#1465](https://github.com/gpsaggese/helpers/issues/1465)
  - Related: [#1447](https://github.com/gpsaggese/helpers/issues/1447) (use `uv`
    instead of `pip`), [#1433](https://github.com/gpsaggese/helpers/issues/1433)
    (pay tech debt)
  - Root cause: the repo grew inside one company's infrastructure and kept its
    assumptions after it became a standalone library

## Users and Use Cases

- **Maintainer of `helpers`**: build the image, run the tests, and release, with
  only a GitHub account
- **New contributor or outside project**: clone the repo, pull the dev image, and
  run the invoke tasks and the tests, with no company account and no company env var
- **Downstream repo** (a repo that includes `helpers` as `helpers_root`): keep
  working after each change, or get a migration note that says what to change
- **AI agent**: execute one PR of the plan, with CI as the gate that says if the PR
  broke something

## Requirements: Build and CI

### `R1` (CI runs without AWS)

- The fast, slow, superslow, and coverage workflows run with no AWS step, no AWS
  credentials, and no AWS repo variable

### `R2` (CI is green on master)

- The latest scheduled runs of the fast and slow test workflows on `master` succeed
  - A test that fails for a known reason is skipped with a link to its issue

### `R3` (Images in the repo owner registry)

- The dev and prod images are pushed to and pulled from `ghcr.io/<repo owner>/`
- No code and no config refers to `ghcr.io/causify-ai` or to Docker Hub `causify`

### `R4` (Reproducible image build)

- Two builds of the dev image from the same commit install the same versions of:
  - The Python packages
  - The tools installed outside Python, e.g., `uv`, `pyright`, Node
- A build does not download a "latest" version of a tool

### `R5` (Lint runs pyright in the container)

- `invoke lint` runs the `pyright` step inside the dev container
- Every tool that `linters2/lint.py` or the git hook calls is installed in the image
  at a pinned version, e.g., `pre-commit`, `ruff`

## Requirements: Vendor Neutrality

### `R6` (No Causify or CK names)

- `git grep -i -E "causify|csfy|cryptokaizen|kaizen"` returns only the matches that
  `03-decisions.md` lists as kept
- A name is made general or the code is removed: no company name is swapped for
  another company name

### `R7` (Invoke works without company env vars)

- `invoke --list` and the common invoke tasks (e.g., `docker_pull`,
  `run_fast_tests`, `lint`) work in a fresh shell where no `CSFY_*` env var is set

### `R8` (No AWS infrastructure)

- `repo_config.yaml` has no `s3_bucket_info` and no ECR registry
- No invoke task:
  - Logs in to ECR
  - Creates or updates an ECS task definition
  - Uploads to an S3 bucket
- The dev image does not install the AWS CLI

### `R9` (Optional AWS library)

- The AWS helper modules stay importable, with the same public functions
  - E.g., `helpers.hs3`, `helpers.haws`, `helpers.hsecrets`, `helpers.htranslate`
- The test suite needs no AWS account: AWS tests use mocks
- A user configures the AWS helpers with the standard AWS env vars or an AWS profile,
  not with `CSFY_AWS_*` env vars

## Requirements: Package Management

### `R10` (uv is the only package manager)

- The image installs the Python packages with `uv` from a committed lock file
- Neither the image nor the thin environment installs Poetry
- `git grep -i poetry` returns only the matches that `03-decisions.md` lists as kept

### `R11` (Lock file changes only on request)

- A default image build uses the committed lock file without resolving the versions
  again
- Updating the lock file needs an explicit option of the build task

## Requirements: Repo Layout and Dev Tools

### `R12` (Clean repo root)

- The repo root has no empty, stale, or one-developer files
  - The list of files to remove is in `04-plan.md`
- `git status` shows no generated scratch file after the invoke tasks run
  - E.g., `tmp.*`, `instr*.md`, `tags`

### `R13` (One linter framework)

- `linters/` and `import_check/` do not exist at the repo root
- `linters2/` holds all the linters and no module imports `linters.`
- `mypy.ini` does not exist

### `R14` (Dev tools fail loudly)

- A misspelled pytest marker fails the test collection
- The Docker-in-Docker setup returns a non-zero exit code when the Docker engine
  does not start
- The git hook fails when a tool that it needs is missing, instead of skipping the
  check

### `R15` (Dev setup survives a moved repo)

- The git hooks keep working after the repo folder is moved or renamed
- The thin environment adds to `PATH` only the dirs that hold executables
  - No `__pycache__`, `test`, `outcomes`, or `old` dir

## Requirements: Docs

### `R16` (Docs site publishes from master)

- A workflow publishes the `docs/` Markdown to a site and succeeds on `master`
- The site has:
  - Full-text search
  - A sidebar built from the folder structure
  - Mermaid diagrams and math
- The site needs no vendor account to build or host

### `R17` (Docs match the dev system)

- No doc describes a removed tool or file as current
  - E.g., Poetry, MkDocs, ECR, `mypy`, `devops/compose/docker-compose.yml`

## Requirements: Compatibility

### `R18` (No new test failures)

- After each PR, the fast and slow tests have no new failures compared to `master`
  before the PR

### `R19` (Migration notes for downstream repos)

- A PR that renames or removes any of these lists it in its description, with the
  replacement:
  - An env var
  - A `repo_config.yaml` key
  - A file that `create_all_helpers_links.py` links
  - A public function or invoke task

## Non-Goals

- Remove the AWS library modules (`hs3`, `haws`, `hmoto`, `hsecrets`, `htranslate`)
  or the `boto3` and `moto` dependencies
  - A follow-up project decides it, see "Open Questions"
- Change the behavior of the `helpers` library functions beyond the renames
- Redesign the invoke task system or the thin environment
- Port the downstream repos: this project writes the migration notes only
- Migrate the blogs that the `website` repo publishes

## Constraints and Assumptions

- The repo is `gpsaggese/helpers`, owned by a user account, not by an org
  - GHCR packages live under `ghcr.io/gpsaggese/`
- The downstream repos depend on `helpers` in two ways:
  - They link files from `helpers_root/` with
    [`create_all_helpers_links.py`](/dev_scripts_helpers/thin_client/create_all_helpers_links.py)
  - They read keys of their own `repo_config.yaml` through `helpers`
- The CI test workflows skip draft PRs
- Most items of [#1465](https://github.com/gpsaggese/helpers/issues/1465) are
  correct, but some are done in a certain way for a reason
  - The reviewer of each PR confirms the items before they are removed
