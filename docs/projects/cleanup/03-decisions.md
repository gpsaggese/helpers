# Cleanup Decisions

- Generated by `.claude/skills/architecture.write_design/SKILL.md`
- One decision per H3, newest at the bottom of its section
- `accepted` means a maintainer chose it; `proposed` means it waits for the review of
  this PR

## Process

### `D1` (Keep the project docs in the docs tree)

- **Decision**: put the docs of the project in `docs/projects/cleanup/`
  - The dir plays the role of `<project>/docs/` in `.claude/skills/project.rules.md`
- **Why**: the project changes the whole repo, so it has no code dir of its own, and
  a new dir at the repo root goes against
  [`R12`](/docs/projects/cleanup/01-prd.md#r12-clean-repo-root)
- **Alternatives**:
  - `HelpersTask1465_Cleanup/docs/` at the repo root, like the `UmdTask<N>_` project
    dirs of `umd_classes`
  - `docs/planning/cleanup/`, next to the generic planning guides
- **Status**: accepted (2026-11-28)

### `D2` (The plan file is the source of truth)

- **Decision**: [`04-plan.md`](/docs/projects/cleanup/04-plan.md) is the source of
  truth of the plan once this PR is merged
  - The body of [#1465](https://github.com/gpsaggese/helpers/issues/1465) points to
    the docs instead of repeating them
  - Agents and people tick the PRs in the plan as they merge
- **Why**:
  - A reviewer edits a file in a PR directly, instead of writing a comment about the
    issue
  - Two copies of the plan drift apart
- **Alternatives**: keep the issue body as the source and mirror it in the docs
- **Status**: accepted (2026-11-28)

### `D3` (Group the PRs by theme)

- **Decision**: group the work in themes, one component letter each, and cut the PRs
  inside each theme
  - `B` build and CI, `R` rename, `U` `uv`, `A` AWS, `D` dev image, `C` repo root,
    `L` linters, `T` test and dev tools, `W` docs site
- **Why**: requested in the
  [review comment](https://github.com/gpsaggese/helpers/issues/1465#issuecomment-7211164749)
  on #1465, so that each theme is one deliverable that can be reviewed and demoed
- **Alternatives**: the ten PRs of #1465, cut by area of the repo
- **Status**: accepted

### `D4` (Order the themes as build, rename, uv, AWS)

- **Decision**: run the themes in this order:
  1. `B`: get CI green
  2. `R`: rename the Causify and CK names
  3. `U`: replace Poetry with `uv`
  4. `A`: remove the AWS infrastructure
  5. `D`: clean up the dev image
  6. `C`, `L`, `T`: clean up the repo root, the linters, and the dev tools
  7. `W`: replace MkDocs
- **Why**:
  - While CI is red, no PR can show that it adds no new failures, per
    [`R18`](/docs/projects/cleanup/01-prd.md#r18-no-new-test-failures)
  - After `B`, the order follows the review comment on #1465: rename, then `uv`
- **Alternatives**:
  - Remove AWS before the rename, so that the rename touches fewer files
  - Rename first, as in the review comment, with CI still red
- **Status**: accepted (2026-11-28)

### `D5` (Update tasks.py in the PR that changes a task)

- **Decision**: each PR that removes or renames an invoke task also updates
  [`tasks.py`](/tasks.py), instead of one `tasks.py` PR at the end
- **Why**:
  - `tasks.py` imports every task: a PR that deletes a task and leaves its import
    breaks every `invoke` command
  - Each item of the `tasks.py` PR of #1465 belongs to one theme:
    - `ECR_BASE_PATH` read from `CSFY_ECR_BASE_PATH`: `R`
    - AWS and ECS tasks, `gh_publish_buildmeister_dashboard_to_s3`: `A`
    - The `oms.lib_tasks_binance` import block: `R`
- **Alternatives**: one PR at the end, as in #1465 (PR10)
- **Status**: proposed

## Scope

### `D6` (Make the code general or remove it)

- **Decision**: for every company-specific item, make the code general or remove it
- **Why**: swapping one company name for another keeps the problem
- **Alternatives**: rename the company names one to one
- **Status**: accepted

### `D7` (Remove the AWS infrastructure and keep the AWS library)

- **Decision**:
  - Remove the AWS step of CI, ECR, the ECS tasks, the S3 buckets of
    `repo_config.yaml`, the S3 uploads, and the AWS CLI of the image
  - Keep the AWS library modules (`hs3`, `haws`, `hmoto`, `hsecrets`, `htranslate`)
    and the `boto3` and `moto` dependencies
- **Why**:
  - No test needs a real AWS account, see `07-progress.md` findings
  - The library modules are public API that downstream repos may import
    - E.g., `hparquet`, `hpickle`, `hcsv`, and `hcache_simple` read `s3://` paths
      through `hs3`
- **Alternatives**:
  - Remove all of AWS, library included: breaks the downstream repos that use it
  - Remove the infrastructure now and the library in a follow-up project
- **Status**: accepted (2026-11-28)

### `D8` (Leave the AWS env vars to the AWS theme)

- **Decision**: the rename theme `R` does not touch the `CSFY_AWS_*` and
  `CSFY_ECR_*` env vars; the AWS theme `A` removes or renames them
- **Why**: `A` comes after `R`
  ([`D4`](#d4-order-the-themes-as-build-rename-uv-aws)), and `A` deletes most of
  these env vars: renaming them first is wasted work in 38 files
- **Alternatives**: rename every `CSFY_*` env var in `R`
- **Status**: accepted (2026-11-28)

### `D9` (The kept AWS library reads the standard AWS env vars)

- **Decision**: the AWS library reads `AWS_PROFILE`, `AWS_DEFAULT_REGION`,
  `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and `AWS_SESSION_TOKEN`, which
  `boto3` and the AWS CLI already read
- **Why**: a user configures AWS once for every tool, and no company prefix is
  needed, per [`R9`](/docs/projects/cleanup/01-prd.md#r9-optional-aws-library)
- **Alternatives**: rename `CSFY_AWS_*` to `HELPERS_AWS_*`
- **Status**: proposed

### `D10` (Rename the company env vars with the HELPERS prefix)

- **Decision**: rename each `CSFY_*` env var that stays to `HELPERS_*`
  - E.g., `CSFY_HOST_GIT_ROOT_PATH` -> `HELPERS_HOST_GIT_ROOT_PATH`
  - Remove the env vars that only the CK infrastructure uses, e.g.,
    `CSFY_TELEGRAM_TOKEN`
  - Use a standard env var when one exists, e.g., the `CI` env var that GitHub
    Actions sets instead of `CSFY_CI`
- **Why**: the review comment on #1465 asks to rename the CK names to `helpers`, and
  `helpers` is the name of the repo, not of a company
- **Alternatives**:
  - No prefix: names like `HOST_GIT_ROOT_PATH` can clash with other tools
  - A shorter prefix, e.g., `HLP_`
- **Status**: proposed

## Build and Registry

### `D11` (Publish the images to the GHCR of the repo owner)

- **Decision**: push and pull the dev and prod images at `ghcr.io/<repo owner>/`,
  with the owner taken from the repo (`ghcr.io/gpsaggese/` today)
- **Why**:
  - Until the repo moved on 2026-11-02, CI pulled `ghcr.io/causify-ai/helpers:dev`,
    a private package of another org
  - CI already sets `ghcr.io/${{ github.repository_owner }}` for the image path,
    which now points to `ghcr.io/gpsaggese`
- **Alternatives**: keep pulling from `ghcr.io/causify-ai`
- **Status**: accepted (2026-11-28)

### `D12` (Replace Poetry with uv)

- **Decision**: install the Python packages of the image with `uv`, from a
  `uv.lock` file, and remove Poetry from the image, the thin environment, and the
  tools
- **Why**:
  - `uv` is already in the image and runs the `uv run` scripts
  - One package manager instead of two
  - Settles the open choice of
    [#1447](https://github.com/gpsaggese/helpers/issues/1447)
- **Alternatives**: keep Poetry for the lock file and `uv` for the scripts
- **Status**: accepted

### `D13` (Build the image from the committed lock file)

- **Decision**: a default image build runs `uv sync` from the committed `uv.lock`;
  an explicit option updates the lock file
- **Why**: `--poetry-mode` defaults to `update` today, so each build resolves every
  version again and two builds of one commit can differ, against
  [`R4`](/docs/projects/cleanup/01-prd.md#r4-reproducible-image-build)
- **Alternatives**: keep "update" as the default and commit the new lock file after
  each build
- **Status**: proposed

### `D14` (Keep the image dependencies apart from the root pyproject)

- **Decision**: keep the dependency file of the image in `devops/docker_build/`,
  apart from the root `pyproject.toml`
- **Why**: a change of the lint config in the root `pyproject.toml` must not
  invalidate the Docker cache of the package install
- **Alternatives**: one `pyproject.toml` at the root for the tools and the
  dependencies
- **Status**: proposed

### `D15` (Prefer Docker-in-Docker over sibling containers)

- **Decision**: run the dockerized tools with Docker-in-Docker on every host, with a
  volume for `/var/lib/docker`, and remove the sibling-container path
- **Why**, from the tests of 2026-11-26 in `07-progress.md`:
  - Docker-in-Docker works on Mac with `--privileged`, although
    `hserver.enable_privileged_mode()` says that it does not
  - Sibling containers need host paths and a root-only socket
  - With a volume, `overlayfs` works and the images are smaller than with `vfs`
- **Alternatives**: keep both paths, sibling containers on Mac
- **Before accepting**: run the dockerized-tool tests with Docker-in-Docker on a
  Mac, since today they run only on Mac and only with sibling containers
- **Status**: proposed

### `D16` (Create the container user in the entrypoint)

- **Decision**: start the container as root with `HOST_UID` and `HOST_GID`; the
  entrypoint creates the user if missing, does the root-only setup, and switches to
  the user with `setpriv`
  - Keep a single sudoers rule: `%sudo ALL=(ALL) NOPASSWD:ALL`
- **Why**: [`create_users.sh`](/devops/docker_build/create_users.sh) and
  [`etc_sudoers`](/devops/docker_build/etc_sudoers) work only for host IDs 0, 501,
  and 1000-1050, and `useradd -u 1000` fails on `ubuntu:24.04`, which already has the
  user `ubuntu`
- **Alternatives**: keep creating the users at build time and extend the ID range
- **Status**: proposed

## Layout and Docs

### `D17` (Keep only linters2)

- **Decision**: move `import_check/` into `linters2/`, port the code that
  `linters2/` still imports from `linters/`, then delete `linters/` and `mypy.ini`
- **Why**: two linter frameworks, and `linters/test/conftest.py` already skips all
  the old tests
- **Alternatives**: keep `linters/` as a library for `linters2/`
- **Status**: accepted

### `D18` (Publish the docs as a static site on GitHub Pages)

- **Decision**: pick the new docs platform among the static site generators that
  build in CI and host on GitHub Pages, e.g., Docusaurus, Starlight, VitePress
- **Why**:
  [`R16`](/docs/projects/cleanup/01-prd.md#r16-docs-site-publishes-from-master)
  asks for no vendor account, and the hosted platforms listed in #1465 (Mintlify,
  GitBook, Read the Docs) need one
- **Alternatives**: a hosted platform, which drops the "no vendor account"
  requirement
- **Status**: proposed

### `D19` (Disable the MkDocs workflow until the new site exists)

- **Decision**: disable the schedule of
  [`publish_mkdocs.yml`](/.github/workflows/publish_mkdocs.yml) in the build theme,
  and delete the workflow when the new site publishes
- **Why**: the workflow fails every day since 2026-05-01 and makes the build look red
- **Alternatives**: leave it failing until the docs theme replaces it
- **Status**: proposed
